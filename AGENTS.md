# Stash — File Management S3

## Overview

**Stash** is a single-user, Drive-style image manager built as one **Guren** (Bun, Laravel-inspired) fullstack TypeScript monolith over any S3-compatible storage.

This file has two parts:

1. **Guren harness** (generated by `bunx create-guren-app`): the framework's agent workflow, commands, and rules. Never delete the harness's hooks or rules.
2. **Project: Stash** (further below): the project-specific constraints, rules, and definition of done.

Where the two overlap, the Stash rules are additive and stricter. Claude Code reads `CLAUDE.md`, so make sure it contains the line `@AGENTS.md`.

## Session Workflow

Nothing runs these steps for you automatically (hook support varies by agent),
so make them part of your loop:

1. **At session start**, run `bunx guren context` and read the output. It ends
   with a "Guren API Signatures" digest of the ORM, controller, and testing
   APIs — read it before writing any code. With the MCP server connected, the
   `guren_get_context` tool returns the same map.
2. **After editing** routes, controllers, models, `db/schema.ts`, or pages,
   run `bunx guren check` and fix what it reports before moving on. With an
   `.oxlintrc.json` in the app (`bunx guren add lint`), run `bun run lint` on
   what you edited as well; its warnings are for you to act on.
3. **When the change is complete**, run `bunx guren gate` and fix what it
   reports until it exits 0. It runs the stages CI runs — codegen, typecheck,
   lint, `check`, `audit`, and the test suite — and a change is not done
   while any of them fails. `--changed` narrows `check` and lint to the files
   you touched. Cursor and Codex run it for you from a stop hook
   (`.cursor/hooks.json`, `.codex/hooks.json`) when a turn ends with
   uncommitted changes, feeding the findings back into the turn (Codex asks
   you to trust the hook once, via `/hooks`; Cursor reads the config from the
   workspace root, so open the app as its own workspace); Copilot and
   OpenCode have no such hook, so run it yourself. The hook also reports
   `audit` warnings on files you changed (a mutating action with no
   authorization, request data in a force write), which never fail the gate. The same hook verifies the
   plan step `bunx guren plan:next` marked (`plan-implement` skill); without
   it, run `bunx guren plan:verify <plan> --step <id>` yourself before
   committing the step.
4. Framework-managed files (`.agents/rules/`, `.agents/skills/`) can be
   refreshed anytime with `bunx guren agent:sync`.

Reusable skills (SKILL.md, the Agent Skills format) live in
`.agents/skills/` — agents that support the standard discover them there
automatically.

Detailed, verified API rules live in `.agents/rules/*.md`; each file's `paths`
frontmatter states which paths it covers — read the matching rule before
editing those paths.

The rule files: `orm-models.md` (models, mass assignment, queries that bite),
`controllers-http.md` (validation, Inertia, auth), `routes-codegen.md`
(registering routes, codegen), `testing.md` (TestApp, assertions, common
mistakes), `docs-and-spec.md` (docs under `docs/`), `comments.md` (what a
comment may carry), `ui.md` (design tokens and the red budget on pages).
Most end with what their full reference under
`.agents/skills/guren-api/reference/` adds; read that file only when the task
needs it. For framework signatures, check the `guren context` digest first,
then the matching rule; only read `node_modules/@guren/*` for APIs neither covers.

## Architecture Overview

`routes/web.ts` registers routes on a `Router`, each pointing at a
`[Controller, 'method']` tuple. A route's Zod `body`/`query`/`params` schemas are
validated before the action (422) and feed `bunx guren codegen`. Controllers read
`this.validated('<route name>')`, query models and render Inertia pages or JSON.
The signatures are in the `guren context` digest; each file kind's rules attach
from `.agents/rules/` when you open it.

# Project: Stash

Project-specific rules. They add to, and never replace, the Guren harness above.

## Start here

1. Read `PLANNING.md`, then `TASKS.md`. Specs live in `docs/` (`IMAGE_PIPELINE.md`, `ROUTES_SPEC.md`, `UI_SPEC.md`).
2. Run `bunx guren context` (see Session Workflow) before writing code.
3. Take the **first unchecked task** in `TASKS.md`. Do only that task. Tick it when every acceptance criterion (AC) is met.
4. If the spec is ambiguous, choose the simplest option consistent with `PLANNING.md` and write one line in the TASKS "Decision log". Ask only if blocked.

## Do not guess Guren

Guren is new and its APIs are not in your training data. Before writing code against a Guren feature:
- Run `bunx guren context <Entity>` for a project map with real signatures, and `bunx guren graph` for wiring.
- Read the guide as raw Markdown: `https://guren.dev/docs/guides/<name>.md` (index: `https://guren.dev/llms.txt`, everything: `https://guren.dev/llms-full.txt`). Most relevant: `routing`, `controllers`, `validation`, `models`, `database`, `storage`, `authentication`, `sessions`, `csrf`, `views`, `frontend`, `testing`, `scheduling`, `console`, `rate-limiting`, `health-checks`, `deployment`.
- Prefer a generator (`bunx guren make:*`, `bunx guren add *`) over hand-writing boilerplate.
- When docs and memory disagree, the docs win.

## Hard constraints

- **Guren is the framework. One monolith: one repo, one `package.json`, one process.**
- **Never add or import** Elysia, Next.js, Express, Fastify, Koa, or `hono` directly. (Guren uses Hono internally; use Guren's router, middleware, and controllers, never Hono's APIs.) No second server, no separate API service, no custom `Bun.serve`.
- **Database: SQLite only**, via Guren models and Drizzle. No other database, no ORM besides Guren/Drizzle.
- **Storage: only through `storage.disk()`** (Guren `StorageManager`). No `@aws-sdk/*`, no `Bun.s3` in app code, no backend-specific calls (SeaweedFS filer, MinIO admin, etc.). The app must work by changing env vars only. See `PLANNING.md` §10.
- **Do not use Guren's Attachments layer** (decision D3). Use `ImageStore` over `storage.disk()`.
- **Images only.** Reject everything else with 415. SVG and HEIC are rejected in v1.
- **Image encoding: `sharp` only**, wrapped in `app/Services/ImageConverter.ts`. Nothing else imports `sharp`.
- No new dependencies without a one-line justification in the commit message.
- No multi-user features. No `/register` route, ever.

## Authorization rules (critical)

- **Every** `POST`, `PUT`, `PATCH`, `DELETE`, and every private page is registered inside the `auth` middleware group (`requireAuthenticated`).
- The **only** public routes are: `GET /i/*`, `GET /t/*`, `GET /p/:publicId`, `GET /health`, and the login routes. Adding a public route requires updating `PLANNING.md` §9 and `docs/ROUTES_SPEC.md`.
- Keep the **route-guard test** (`tests/route-guard.test.ts`) green: it enumerates all registered non-GET routes and asserts that an unauthenticated request does not succeed (401/302/403, never 2xx). Add new routes to that sweep automatically; do not hand-maintain a list unless the graph is unavailable.
- Use `this.auth.userOrFail()` in mutating actions as defense in depth.
- Use `this.validateBody()` / `validateParams()` / `validateQuery()` with zod on every input. `guren audit` must stay clean.

## Public image routes (critical)

- Responses carry **no `Set-Cookie`**. Verify (the session and CSRF middleware may attach cookies to GETs), and mount or configure the routes so they don't. A test asserts it.
- Exact headers and URL rules are in `docs/IMAGE_PIPELINE.md` §5 to §6. Always send `X-Content-Type-Options: nosniff`.
- Do the DB lookup and the `If-None-Match` check **before** reading storage, so `304` never touches S3.
- Trashed or missing images and versions return `404`.
- Never derive a storage key from user input. Keys come only from DB rows (`storage_key`).

## Versioning rules (critical)

- `(publicId, version)` is **immutable**. Never overwrite an existing version's object. Replace = write version `n+1`, then flip `images.current_version` in the same DB transaction as the new `image_versions` row.
- Rename, move, and star never bump the version.
- The `{slug}` URL segment is cosmetic; resolve by `publicId` + `version` only.
- Prune old versions only beyond `KEEP_VERSIONS`, oldest first, objects before rows.

## Image pipeline rules

- Order: size cap → sniff → pixel cap → auto-rotate → optional resize (never enlarge) → encode → **strip metadata (EXIF/GPS)** → thumb → sha256 → store → DB. Details: `docs/IMAGE_PIPELINE.md`.
- Never trust the client MIME or file extension. Trust the sniffed format.
- Cap concurrent encodes (`CONVERT_CONCURRENCY`, default 2). AVIF is expensive.
- If an object write succeeds and the DB write fails, delete the orphaned objects. Never leave orphans.
- Probe AVIF/WebP capability at boot; expose it as a shared Inertia prop and hide unavailable formats.

## Conventions

- TypeScript strict, no `any`. Follow the scaffold's path aliases and file layout (`app/Http/Controllers`, `app/Models`, `resources/js/pages`, `routes/*`, `db/schema.ts`).
- Controllers stay thin: validate → call a service or model → respond. Logic lives in `app/Services/*`.
- Shape props with API Resources (`JsonResource`) so pages get typed props; no `fetch` between controller and page for page data. Use Inertia navigation and `router.reload({ only: [...] })`.
- JSON responses are allowed only for: the upload endpoints (progress and per-file results) and `/health`.
- The upload queue uses `XMLHttpRequest` (for progress events) and sends the `X-XSRF-TOKEN` header from the `XSRF-TOKEN` cookie.
- UI: React + Tailwind + shadcn/ui + lucide-react. Read `docs/UI_SPEC.md`. No other component libraries.
- Env: declare every variable in `config/env.ts` (validated at boot). Never read `process.env` elsewhere.
- Names: services PascalCase files, components PascalCase, routes named with `.name('area.action')`. Keep files under about 250 lines.
- Comments explain *why*, not what.
- Architecture decisions go in `docs/adr/` following the scaffold's seed example (or `bunx guren make:adr "..."`). Do not invent front-matter; copy the seed's.

## Security checklist

- Sanitize file names (strip path separators and control characters). Slugs are `[a-z0-9-]` only.
- Do not serve user content as HTML or SVG. Pinned and latest routes only serve the stored `avif`, `webp`, `jpeg`, `png`, `gif` MIME types.
- Public routes: rate-limit with Guren's rate limiter (task 5.2). Login is already throttled.
- Never log credentials, `APP_KEY`, or storage secrets. Never commit `.env`.
- `ADMIN_PASSWORD` is used only by the seeder; store only the hash.

## Testing

`bun:test` + `@guren/testing`; requests run in-process through `TestApp`, no server. Framework rules: `.agents/rules/testing.md`.

- Use the **memory** storage driver in unit tests; the contract test also runs against the real endpoint when `RUN_S3_TESTS=1`.
- Generate fixture images in tests with `sharp` (no binary fixtures committed).
- Must-have tests: converter (formats, resize, metadata stripped, animated GIF), versioning (replace, prune, pinned stays valid), public routes (headers, 304, 404, no cookie), route guard, folder cycle rejection, trash/restore/purge (objects deleted), storage contract.
- Add or update tests in the same change as the feature.

## Git

- Small commits, imperative: `feat(upload): convert and store image version 1`.
- One task per commit where possible. Never commit `data/`, `storage/`, `.env`, or `node_modules/`.

## Definition of done (any task)

- ACs in `TASKS.md` met and ticked; `bun run typecheck`, `bun test`, and `bunx guren gate` pass.
- Loading, empty, and error states exist for every new screen.
- No dead code, no `console.log`, no TODO without a `TASKS.md` entry.
- Specs updated if behavior or routes changed (`ROUTES_SPEC.md`, `IMAGE_PIPELINE.md`, `UI_SPEC.md`); run `bunx guren spec:generate` for generated spec views.

## Do not

- Do not restructure the layout in `PLANNING.md` §12 without updating it.
- Do not "improve" finished tasks in passing. Add ideas to the TASKS backlog.
- Do not weaken a failing test or silence a `guren audit` finding to get green. Fix the cause.
